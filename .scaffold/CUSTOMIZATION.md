# Customize a generated application

Initialize once with scripts/init.mjs before installation. Dry-run validates without writing; --reconfigure changes supported ports/description without renaming identity or changing scaffold lineage. Existing local configuration is preserved.

Start from the memory CRUD and the contract in packages/api. Introduce new domain types in core, repository methods in db, routes in createApp and calls in frontend/src/api. Keep API routes under /api. Add pages using the single lazy route list. Delete the example when replacing it with real business behavior.

Adopt optional capabilities individually from the versioned maintainer recipes. Record exact files, dependencies, configuration and validation in the application's own documentation. Do not add a preset selector, dynamic plugin loader or dependency container. Persistence, real login and public deployment require their own explicit implementation and verification.

For portable user settings, define the application-owned payload in `packages/core/src/settings`, create a settings codec with stable `applicationId` and `documentType`, retain sanitized fixtures from schema v1, and add every one-step migration before releasing the new schema. Inject a memory or file `SettingsRepository` through the existing `createApp(options)` boundary. File loading backs up exact old bytes before persisting a migrated canonical document; import supports side-effect-free preview, backup-protected commit and restore. Treat migration failure as a readiness failure and never replace invalid data with defaults. Keep `.env`, ports, log levels and runtime paths as startup configuration only. Keep process identity, locks and transient health state in the lifecycle layer; never mix either category into an exported settings document.
